## Two traps LAAM's BootSequence was hiding (both fixed here)
- LAAM's `BootSequence` doubled as the **font-load synchronizer** (`document.fonts.ready`).
  Dropping it silently removed that. Without it: (a) the hero timeline plays against the
  fallback face inside `overflow-hidden` masks and snaps when Archivo swaps in; (b)
  `revealOnScroll` computes `once: true` triggers pre-font, the swap moves the document,
  and a section that "fired" while offscreen stays at `opacity: 0` **forever**.
  Fix: hero timeline built `paused: true`, played on `document.fonts.ready` **with a 1200ms
  timeout failsafe** (load-bearing — `immediateRender` parks the headline offscreen, so a
  blocked Google Fonts request would mean no headline at all); plus
  `document.fonts.ready.then(() => ScrollTrigger.refresh())` in App.
- `applyDocumentLocale()` must run **synchronously in main.tsx before createRoot().render()**,
  not in a `useEffect`. `index.html` ships `lang="vi"`; in an effect, `?lang=en` paints one
  frame of English copy at Vietnamese display leading (~30% line-height jump on the largest
  type). Verified at DOMContentLoaded: EN -> `.94`, VI -> `1.24`.

## Hero WebGL backdrop ("the deal core") — added after user feedback
User said the hero, especially the right-hand panel, was flat and wanted a wow moment
(explicitly offered three.js). Built `src/lib/deal-scene.ts` (framework-free) +
`src/components/hero/DealStage.tsx` (lifecycle only).

- **Concept is the page's own argument**: documents stream in -> absorbed into a lit
  core -> three beams out. **THREE outputs, not four**, even though the tab row has
  four: `Flow.tsx` already states the master record is neither a document nor an
  output. So **Records IS the core** — that tab focuses/swells the core and stands the
  beams down instead of lighting one. Four symmetric beams would have contradicted a
  section shipped two screens below.
- **Backdrop, not a panel — because of a measurement.** At 1440x900 the hero's right
  column is only 214px tall in a 604px slot, and the VI headline pushes it ~130px
  lower. Nothing worth looking at fits. Scene is offset into the empty top-right
  quadrant (78% across / 27% down), derived from visible world size so it holds at any
  aspect ratio, with a radial mask keeping it off the type.
- **Camera must `lookAt(0,0,0)`.** Compensating the lookAt toward the group pulled the
  composition back to centre and onto the headline. With lookAt at origin, a group
  offset at z=0 maps 1:1 to NDC, so the two numbers in `layout()` ARE the screen
  position.
- **Gate is `min-width: 1120px`** — the exact width where the hero splits into two
  columns. At 1024 (single column) the scene landed on the prose. Narrower = further
  right + smaller, never drifting back to centre.
- **Budget held via dynamic import**: entry chunk 125.66 kB gzip (<150 kB rule),
  `deal-scene-*.js` 132.88 kB gzip, and `dist/index.html` does NOT preload it (verified
  by grep). A static import would silently fold 130 kB into the entry.
- **Perf measured**, 1440x900 @ 4x CPU throttle: p50 8.3ms, max 9.4ms, 0 frames >20ms.
  rAF stops when hero offscreen / tab hidden; DPR capped 1.75; frame delta clamped so a
  backgrounded tab doesn't teleport docs through the core.
- **Reduced motion never downloads the three.js chunk** (verified via
  `performance.getEntriesByType('resource')`) — guard is at the source, not visual.
- Tab state lifted from `Console` to `Hero` (`onActiveChange`) so tabs drive both the
  panel copy and the beam. Hover/focus/touch pause now freezes the scene too — decided,
  documented.
- Also fixed: `vite.config.ts` still carried LAAM's comment referencing `SplineStage`,
  a component that does not exist here.

## Round 3 (user: "mấy cái đường line nối bảng với quả cầu không đẹp")
Beams were a 1px `THREE.Line` + a floating corner-bracket `LineSegments` at the far end.
They read as CONSTRUCTION GEOMETRY — three hard strokes fanning down from a sphere made
the core look like it stood on a tripod, and the brackets marked nothing nameable.

Replaced with **soft light cones**: one shared `CanvasTexture` (generated per-pixel via
`createImageData`) mapped onto a `PlaneGeometry(1,1)` quad per beam, stretched between
the two endpoints and rotated by `atan2(dy,dx) - PI/2` (PlaneGeometry local +Y runs
along the beam, which is also the texture's `v` axis).
- Texture: `v` = along the beam (v=0 at core); `fade = (1-v)^1.4 * 0.66 + 0.34` — the
  0.34 FLOOR matters, a beam that fades out before arriving lands on nothing.
  `halfWidth = 0.09 + v*0.26` (gaussian across `u`, so no outline).
  ⚠️ ImageData row 0 is the TOP of the canvas but PlaneGeometry puts v=0 at the BOTTOM —
  so the core end is the LAST row: `const v = 1 - y/(h-1)`.
- Bracket node -> a small bright `Sprite` glow ("the landing"). Dock point lifted to
  `rect.top - 10` because a sprite centred ON the panel edge hides half of itself behind
  the panel.
- `shaft.renderOrder = -1` so atmosphere never draws over the core/documents.
- Idle opacity 0.2, active 0.82 — three faint cones at rest keep the "three outputs"
  reading without clutter.
- **Round 3b — "nhìn như nó bị cắt đi".** The gaussian only softened the SIDES (`u`);
  both ENDS were still the raw quad edge, so the shaft began at a sliced-off straight
  line. A light-shaft texture needs THREE falloffs:
  1. gaussian across `u` — no side outline;
  2. `smoothstep(0, 0.2, v)` fade-in — emerges from the core instead of a cut edge.
     Pair it with starting the quad INSIDE the shell (0.82, not 1.05) so the ramp is
     spent behind the core wireframe and there is no seam;
  3. `1 - smoothstep(0.975, 1, v)` tip taper — **must be tiny**. First try was 0.93,
     which killed the last ~30px and the beam stopped short of the tab it docks on —
     a worse fault than the cut edge it fixed.
- **Round 3c — "tia sáng trông hơi thô"**. Two causes, both about DENSITY not shape:
  1. The cone had a solid body with an obvious brightest region = a painted wedge.
     Fixed: `along` curve flattened `(1-v)^1.4*0.66+0.34` -> `(1-v)^0.9*0.5+0.5`,
     gaussian exponent 2.6 -> 1.7 (slacker = no perceptible edge), shaft opacity
     roughly halved (active 0.82 -> 0.42).
  2. 7 motes at size 0.26 on a SHARED phase marched down the centre line at even
     spacing = a dotted line. Fixed: 30 motes at size 0.1, each with its own
     `{phase, speed, lateral, bright}` seed, `vertexColors: true` so brightness varies
     per particle and fades in/out along the run. Lateral offset is derived from the
     SAME widening the texture draws (so none escapes the cone) and the seed is CUBED
     so most cluster near the centre.
  Principle that came out of it: **the cone is haze, the particles are the beam.**
- **Round 3d — user: "bỏ tia sáng đi, dùng hạt phóng ra đến table".** Took the principle
  to its conclusion: the light cone is GONE (texture generator, shared quad, per-beam
  mesh + material, all disposal). Only the particle stream and the landing glow remain.
  Beam evolution across this session: 1px line + bracket -> light cone + 7 motes ->
  cone + 30 motes -> **52 motes, no cone**.
  - `MOTES_PER_BEAM` 30 -> 52: a count that looks right as dust INSIDE a lit cone looks
    sparse when it is the only thing there. Size 0.1 -> 0.13.
  - Position eased `t ** 1.25` (slight acceleration) = "phóng ra" rather than drifting,
    and it stretches spacing toward the far end so particles don't bunch on arrival.
  - Spread is now `length * (0.035 + 0.115 * along) * seed.lateral` — the fan IS the
    beam shape now, no longer borrowed from the texture's widening.
  - Idle state kept meaningful: `opacity = 0.24 + 0.76 * level`, and the particle colour
    lerps DIM -> SIGNAL by level, so an idle path reads "recorded" and the active one
    reads "running". Without this the tab with no path stops being legible.
  - Removing the cone left `DIM` and `color` unused — the right fix was to USE them for
    the idle tint, not delete them.
- Perf unchanged: 1920x1080 @4x CPU p50 8.4 / p90 16.6 / 2 over 20ms in 200;
  worst case 1920 logical @ DPR2 (3340x1890 buffer) p50 8.3 / p90 8.6 / 0 dropped;
  unthrottled p50 8.3 / p90 8.8 / 0 over 20ms. Additive quads cost nothing measurable.

## Round 4 (user: 3 asks — brighten particles, style the landing glow naturally,
## make the WHOLE hero region sway with the pointer like LAAM_introduce)
- **Particles + landing**: bright range 0.35-0.65 -> 0.5-1.0, size 0.13 -> 0.15. Landing
  sprite FLATTENED (`scale.set(pool*2.1, pool*0.6, 1)` not `setScalar`) — a round glow
  floating above a button read as a ball parked in mid-air; wide+short reads as light
  pooling ON the surface. Also moved from `rect.top - 10` (clear of the edge) to
  `rect.top + 2` (just inside it), so the lower half glows up through the translucent
  panel instead of stopping at the border.
- **The pointer-sway merge — this is the one worth remembering in full.** Before this
  round there were secretly TWO independent parallaxes: the panel's CSS transform (old
  code, still present) and the scene's CAMERA position (still driving world->screen
  projection). They damped independently, so the instant the pointer was off-centre the
  beam docks and the buttons they land on **parted ways** — a live bug the static
  screenshots from every prior round never caught, because none of them moved the mouse.
  - Fix: exactly ONE damped value, computed once per frame in the scene, reported via
    `onDrift(xPx, yPx)` in CSS pixels. `DealStage` writes it as `translate3d` on a new
    `driftRef` wrapper (NOT the `data-anim="console"` element — GSAP owns that one's
    transform for the intro; two writers on one transform node is a guaranteed fight).
    The scene applies the equivalent in WORLD units to `world.position`, never to the
    camera — moving the camera changes where every world position lands on screen, which
    just relocates the bug instead of fixing it.
  - Tab-button measurement now subtracts `driftPx.current` back out before converting to
    NDC, so a dock is always computed at the panel's RESTING position regardless of where
    the pointer happens to be when `ResizeObserver`/`fonts.ready` fires the remeasure.
  - Register: 20px horiz / 13px vert at viewport extremes — matched to LAAM_introduce's
    own hero grid parallax, per the user's explicit ask to feel the same.
  - Reduced motion / narrow viewport: no pointer listener is ever attached (not "sway
    disabled" — never constructed), verified panel transform stays `none` in both cases.
- **Perf trap found BY this merge, real and worth the pattern:** an exponential damp
  toward a resting value never reaches exactly zero, so every frame reported a
  microscopically different drift -> every frame did a `style.transform` write on a
  layer holding live text. Under 4x CPU throttle this alone roughly DOUBLED idle frame
  time (8.4ms -> ~16ms, 200 over-20ms is wrong — should read: went from 0 dropped frames
  to double-digit dropped frames). Fix: deadband — stop calling `onDrift` once the change
  since the last emitted value is <0.05px. After the fix: 4x throttle idle AND
  pointer-sweeping both back to p50 8.3-8.4ms, 0-2 over 20ms.
- **False-positive trap during this measurement, worth remembering for ANY future perf
  check on this project**: multiple browser tabs each running their OWN copy of the
  WebGL scene compete for the same throttled CPU budget. A second `AM_introduce` tab left
  open (from earlier screenshot rounds) alone was responsible for what looked like a real
  regression (idle 4x-throttle p50 16ms) before it was closed. **Always close duplicate
  tabs before trusting a throttled perf number.**

station+label was `className="absolute"` with only `top` set — no `left`/`right`/
width. An absolutely-positioned box with neither inset set on an axis shrinks to
fit content, and since BOTH children (`Station` mark + label span) are themselves
`position: absolute` (removed from flow), the li's shrink-to-fit width collapsed to
~0. Left-lane labels (using `left: X`) still worked by coincidence (measuring from
a near-zero-width box's left edge ≈ true left edge), but right-lane labels (using
`right: X`) measured from a near-zero-width box's RIGHT edge, landing miles off
target. Fix: `className="absolute inset-x-0"` on the li so both `left` and `right`
children measure from the figure's real edges. **General lesson**: `right:` (or
`bottom:`) on a child inside an absolutely-positioned parent is only trustworthy if
that parent has an explicit/resolved width (or full inset-x-0) — never assume it.
