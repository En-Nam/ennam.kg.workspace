1Maturity summary

DAAB is a knowledge-graph and data-access platform for AI agents. It turns documents and connected business databases into a queryable graph and exposes that graph to MCP clients and a web dashboard. The core pipeline (ingest, graph, search, natural-language database query, agent gateway) is implemented and has been exercised end-to-end with demo data. The platform has not yet run in production.

3.2 Reading the timeline

  • Two build peaks. April delivered phases 2–5: data sources, NL query, accounts and chat. June delivered phases 6–8 (ingestion, entity resolution, GraphRAG, HTTP transport) and ended with release v1.0.0.
  • Post-release work (July to September) is lower in volume. It covered new connectors (MySQL/MariaDB), document management system sync, the gated write path, and hardening of NL-to-SQL accuracy. Commit volume has fallen since July.
  • Specifications and code. Specifications for phases 2 onward were written alongside or ahead of their code. The phase-1 specifications were written after the phase-1 code, to document it.
  • Team. Git history shows 3 distinct author identities after alias merging. That is an identity count, not headcount. Team size and roles: TO BE COMPLETED.

4.3 Practices visible in the code

  • Specification-driven. 43 written specifications: 33 with use cases, numbered business rules and NFRs, and 10 lighter improvement specifications. From phase 2 onward, specifications were written alongside or ahead of the code; the phase-1 specifications document code already written.
  • Versioned schema. 86 paired up/down SQL migrations applied by golang-migrate.
  • Standard-library Go. net/http and database/sql, no web framework and no ORM. Dependency injection happens in one composition root.
  • Security gates at release. A cross-project isolation test suite ran with the race detector against a migrated database before v1.0.0 was frozen.
  • Fail loudly. Ingestion failures are recorded per draft and per document, not swallowed. Extraction parse errors are raised, not returned empty.
  • Auditability. Node history is append-only for graph edits (regenerating a document replaces its sections and chunks), and every database write attempt is audited.
  • Evaluation assets. A merge-precision benchmark and gates for entity resolution, a retrieval evaluation script, and an NL-query benchmark schema.
  • Cost controls in code. Per-run and per-document LLM cost ceilings, content-hash deduplication, and local models for embedding and re-ranking.

5Known limitations

Open items a technical reviewer should know about. None blocks the pre-production uses in §1; the §5.3 items are scheduled before any production tenant.

5.1 Processing and capability limits

AreaCurrent behaviour
Worker job deliveryQueue consumption is at-most-once. A job interrupted by a worker restart is not redelivered automatically. A recovery sweep for stalled entity-extraction runs is implemented but not yet scheduled (PLANNED). Failures inside a job are recorded per item.
PDF lengthAt most the first 50 pages of a PDF are extracted.
Office documentsDOCX files yield paragraph text only; tables are not extracted. Legacy .doc and .xls, PowerPoint (.pptx) and image files are not accepted.
Structured filesJSON, CSV and XLSX are stored at document level. They are not chunked or embedded. One financial-statement layout is parsed deterministically.
Document-level extractionThe per-document LLM summary step reads the first 12,000 characters. Chunk-level extraction covers the whole text.
Code knowledge graphSymbols and containment only. No call or import edges, and no embeddings for code symbols.
Embedding throughputLocal embedding runs on CPU and is not parallelised across worker jobs. Large ingests are serialised on it.
Database write pathSupported for PostgreSQL sources only.
Model cache in the release bundleThe release bundle has no persistent model-cache volume, so embedding models are downloaded again when a container is recreated.

5.2 Engineering quality gaps

  • The web dashboard has no automated tests and no CI. Outstanding lint findings are not enforced.
  • Python has no CI, and coverage measurement is not configured. One unit test fails at the baseline.
  • Two advertised MCP tools have no server route. The gateway's contract tests use mock servers, so they do not catch missing routes.

5.3 Hardening items before production

#ItemTarget state
1Secret managementWire the in-application cloud secrets provider (a stub today) and move the encryption key to a managed key service, held by as few services as possible.
2Transport securityThe agent gateway requires TLS by default on non-loopback interfaces (today it only warns), with a reference TLS reverse-proxy configuration.
3Rate limitingAPI-wide per-key and per-IP rate limiting in the core server, including login, with state shared across replicas. Today only the agent gateway (per identity, in a single process) and the public ingestion endpoint rate-limit.
4Authorization hardeningProject scope is enforced today by middleware and on project-scoped handlers. Target: the same per-project role and ownership check on every project- and data-source-scoped operation and every read by ID, including for service and agent keys that are not linked to a user.
5Dashboard proxyEvery proxied API call requires an authenticated dashboard session, enforced centrally.
6Internal service authenticationAuthenticate the worker service's internal endpoints instead of relying on network isolation.
7Real-time channelsRestrict WebSocket origins to configured hosts and authenticate the progress streams.
8Release data hygieneMove development seed data, including seeded credentials, out of the migrations shipped in the release bundle, and require operator-generated credentials at install time.
9Network exposureThe release bundle publishes no host ports for the database, cache and worker services, and the cache requires authentication. Only the dashboard and the agent gateway are exposed, behind TLS.
10Durable job processingAcknowledged delivery, bounded retries and a dead-letter queue for worker jobs, and a scheduled recovery sweep for stalled extraction runs.
11SQL validation hardeningDatabase-level read-only sessions for every supported engine; today only PostgreSQL sources on the agent/API path have one. The dashboard chat path, where the worker service connects to source databases directly, gains parser-based validation, read-only sessions and server-side statement timeouts. Least-privilege credential guidance for connected databases.
12Cloud deliveryUse the dedicated migration command in the deploy workflows, add CI and container-service delivery for the Python and dashboard services, and bring the managed Redis under infrastructure-as-code.
13Multi-replica readinessCoordinate background workers across API replicas, align HTTP timeouts with the long-poll and streaming endpoints, make the indexer readiness check fail when a dependency is down, and define self-hosted backup, restore and RPO/RTO.
14Security headers and external reviewA content security policy and standard security headers on the dashboard, then an independent penetration test before the first production tenant: TO BE COMPLETED
15Uniform model-call accountingRoute the direct extraction endpoint and the dashboard chat model calls through the same usage log, budgets and circuit breaker as the server's AI layer.

8.4 Method and reproducibility

  • Go: go list -deps over the three command packages to find linked modules; licence text classified from each module's LICENSE file in the local module cache (no network).
  • Python: uv export --frozen --no-dev for the runtime set; License-Expression, License and classifier fields read from installed METADATA.
  • Web: npm ls --omit=dev --all for the production tree; the license field read from each installed package.json.
  • Services: image tags read from the Compose files; the running Redis and pgvector versions read from the development containers.
