1Overview & design principles

DAAB turns an organisation's operational databases and document estate into one queryable knowledge graph. AI agents reach it through a standards-based MCP server (55 tools advertised, 53 of them wired to the API); people reach it through a web dashboard. Underneath is a single PostgreSQL system of record that holds the graph, its version history, full-text indexes and vector embeddings together.

Source engines: PostgreSQL, MySQL, MariaDB, Microsoft SQL Server. Formats: PDF, DOCX, Markdown, TXT, CSV, XLSX, JSON.

What the platform does

  • Connects to live databases. Registers customer PostgreSQL, MySQL, MariaDB and SQL Server sources, extracts their schema, and generates a graph of tables, foreign keys and AI-detected implicit relationships.
  • Ingests documents. Parses, OCRs (including Vietnamese), deduplicates, sections, chunks and embeds documents, then extracts entities and relationships into the same graph.
  • Answers questions over data. For agents, translates a natural-language question into a validated query plan, renders parameterised SQL deterministically and runs it read-only against the source; the dashboard chat adds a conversational mode (Chapter 8).
  • Retrieves knowledge. Offers full-text, semantic and hybrid (Reciprocal Rank Fusion) search, passage-level retrieval with citations, multi-hop traversal and cross-document GraphRAG.
  • Resolves entities. Merges duplicate people, organisations and concepts through a staged, confidence-gated and reversible pipeline.
  • Remembers. Gives agents a durable, scoped memory (remember / recall) with hybrid recall.
  • Writes back, under control. Opt-in single-row inserts and pre-approved multi-step write playbooks, all audited.

Design principles

PrincipleHow it shows up in the code
One transactional system of recordGraph nodes, edges, version history, full-text vectors (tsvector) and embeddings (pgvector) all live in PostgreSQL 16. No separate graph or vector database to synchronise; a write and its index update commit together.
Single write pathThe Go API server owns the database. Graph writes from Python workers, the dashboard and the MCP bridge go through its REST API, so validation, authorisation and audit apply to every writer. The one exception is an optional direct database connection for the worker (set in the development stack) that marks merge suggestions for review and looks up documents.
Schema as configurationNode types, required properties, completeness rules and the edge whitelist are declared in config.yaml and enforced by validation gates. New knowledge kinds need configuration, not new tables.
Versioned historyEvery node update is copied to a versions table by a database trigger, and graph edits never remove versions. Knowledge nodes are deprecated or superseded rather than deleted; the exception is document regeneration, which replaces a changed document's sections and chunks (and their version rows). Updates use optimistic locking.
The model proposes, code decidesFor agent (MCP / API) data queries the LLM returns a structured query plan, never raw SQL; the dashboard's agentic chat lets the model write SELECT statements, checked by a read-only validator with row caps. Merge decisions pass rule, reranker and confidence gates. Write playbooks are proposed deterministically and must be approved before they run.
Local embeddingsEmbeddings (multilingual-e5-small, 384 dimensions) and the reranker (bge-reranker-v2-m3) run on CPU inside the platform. Search and resolution carry no per-call embedding cost, and document text is not sent out to be embedded (an optional hosted embedding service is used only for table selection, when configured).
Provider-agnostic AILLM providers are database-registered with encrypted keys, selected by priority with automatic failover and a circuit breaker. Models are assigned per function (e.g. query planning vs extraction). Dashboard chat and, when configured, chunk-level extraction call providers from the Python services (Chapter 3).
Standard library firstThe Go server uses net/http and database/sql with hand-written SQL, with no web framework and no ORM. That gives it a small dependency surface and predictable queries.
Deployment status: pre-productionDAAB runs today as a self-hosted Docker Compose stack for development and demonstrations LIVE. A release bundle (v1.0.0) and a cloud development environment on AWS (ECS, RDS, ElastiCache) with CI/CD for the Go service are built BUILT; production deployment is PLANNED. No production customers, SLAs or scale figures are claimed in this document. Infrastructure, security and operations are covered in Document 03.

Inside the Go API server

The server is a classic three-layer design wired by constructor injection in a single composition root. Handlers decode requests and authorise; services hold business rules, validation gates and pipelines; stores hold hand-written SQL and transaction helpers.

Request pipeline. Every request passes, outer to inner: request-ID → panic recovery → structured access logging → metrics; routes under /api/ then pass API-key authentication and project resolution before reaching a handler. Project scope is enforced by that middleware and on project-scoped handlers; handlers that receive a project in the request body re-check access against the caller's key, and writes by user-linked keys require a project role (viewer < developer < admin). Applying per-project checks uniformly to every by-ID read and to keys not linked to a user is a hardening item before production (Document 03, Chapter 8). A project that has been archived rejects every mutating method.

AI provider layer. Providers (Anthropic API, Claude subscription via OAuth, OpenAI-compatible endpoints) are registered in the database with encrypted keys and a priority. The selector picks the highest-priority healthy provider, fails over on error, and wraps each provider in a circuit breaker (opens after 5 failures within 10 minutes, half-opens after 30 seconds). A per-function resolver lets administrators assign different models to different jobs. Every call routed through this layer is logged with its token usage and cost for budgeting. Two paths call providers from the Python services instead: dashboard chat, which receives the selected provider's key from the Go server per request, and chunk-level extraction when it is configured with its own endpoint; neither passes through this layer's circuit breaker or usage log.

Configuration. The server reads configuration in four layers, each overriding the one before: config.yaml (the knowledge schema, edge whitelist, completeness, search, AI, cost and resolution settings), then a per-environment YAML file (development, staging, production, self-hosted), then KG_* environment variables, then a system_settings table for runtime overrides and feature flags.

4Knowledge graph model

Every piece of knowledge is a typed node in a single table, with type-specific properties in JSONB and a schema per type declared in configuration. Edges are typed and must match a whitelist of source → relationship → target rules.

Edges and the whitelist

Edges carry a type, JSONB properties (for example confidence and reasoning on AI-detected relations), provenance (creator, session) and a uniqueness constraint on (source, target, type). The edge type is deliberately not constrained in the database: the whitelist in configuration is the single source of truth. It holds 59 rules over 26 relationship labels, each with an optional cross-project permission.

Figure 5. Every graph write passes schema and completeness gates, whitelist checks and optimistic locking; history and search indexes are maintained by database triggers in the same transaction.
  • Gate 1 validates properties against the type's schema; Gate 2 applies completeness rules and profiles (for example, a decision needs a rationale).
  • Optimistic locking: a partial update may carry expected_version; a mismatch returns HTTP 409 instead of overwriting a concurrent change.
  • Version history: an update trigger copies the prior row into knowledge_node_versions (unique on node + version). Nodes move to deprecated or superseded; there is no delete on the node API. When a changed document is regenerated, its old sections and chunks, with their version rows, are removed and rebuilt (Chapter 6).
  • Search vector: a trigger maintains a weighted tsvector (title and name weighted highest, then descriptive, then contextual fields), plus a trigram index on titles.

5.3 Live data sources and schema catalogue

5.4 Queries, conversations and writes

  • Reproducible answers. Every query stores the question, the SQL that was generated and the result, so any answer can be traced back to the exact statement that produced it.
  • Plan cache keyed on schema. Cached plans are keyed by normalised question and schema fingerprint and count their hits; a schema change produces a new fingerprint rather than a stale plan.
  • Playbooks are unique per data source by name, versioned, and record who approved them and when, plus the reason a playbook was marked stale.
  • Write audit captures inputs. Each attempt records actor, operation, target table, input values and outcome, whether it was successful, rejected by a gate, or failed at the database.
  • Conversations keep per-message token counts, latency and model, and link to the query they ran; chat clarifications are held in their own table with an expiry.

6Ingestion pipelines

Knowledge enters the graph by three routes: documents (files and structured drafts), live databases (schema catalogues) and source code (symbols). All three write through the Go API, so every node passes the same validation gates.

6.1 Documents LIVE

Entry points. Dashboard drag-and-drop upload; an MCP client uploading a file out-of-band to the bridge's file endpoint; the public ingest API (single draft or batches of up to 50); and a document-management-system sync, configured as a project source connection, that pages through analysed documents, downloads each through a signed URL, ingests it and discards the temporary copy. Every input becomes a draft node. Drafts are processed immediately or held for approval according to project settings.

Deduplication ("ingest once"). Content is canonicalised (BOM, line endings, whitespace) and hashed. Three tiers apply: (1) the same source with the same hash reuses the node; (2) the same source with a changed hash regenerates: the old sections, chunks and embeddings are removed and rebuilt on the same hub node; (3) the same hash from any other source reuses that node. A lookup error fails the draft rather than risk a silent duplicate.

Structure and embeddings. A Markdown heading tree yields up to 200 document_section nodes per document. A section of up to about 1,500 characters becomes a single document_chunk; larger sections are packed by paragraph into chunks of at most 1,200 characters, splitting on sentences when needed. Each chunk carries its line and character offsets, so answers can cite the exact passage. Entities from the extraction step become project-scoped concept nodes, deduplicated on a diacritic-folded key that also normalises Vietnamese legal-form abbreviations. Reusing concepts across documents is what connects documents to each other. Sections and chunks are embedded with multilingual-e5-small (384 dimensions, L2-normalised, passage: prefix) in batches of 32.

Structured extraction. One LLM call per document (temperature 0, routed through the Go AI layer) returns topic, entities, decisions, referenced tables, referenced APIs and people, keeping names in their original language. It reads the leading 12,000 characters of the document. A second LLM pass proposes cross-source edges (cross_source_reference, references_document, references_component) against up to 80 architecture nodes, and applies those with confidence ≥ 0.5. Tables named in a document are linked to their schema nodes with references_table.

6.2 Live databases LIVE

Connecting a database turns its schema into a navigable part of the graph. Both extraction and graph generation run inside the Go server, extraction on the in-process job engine (3 workers, 3 retries) and generation as a background job, with live progress streamed to the dashboard.

  • Engines: PostgreSQL (lib/pq), MySQL and MariaDB (go-sql-driver/mysql), Microsoft SQL Server (go-mssqldb), each with its own catalogue querier.
  • Explicit relationships come from declared foreign keys; junction tables are detected and turned into many-to-many edges.
  • Implicit relationships are proposed from naming conventions and compatible column types, scored 0–1 by an LLM, and stored with confidence and reasoning. People can confirm, reject or reverse a rejection in the UI.
  • Re-sync refreshes the catalogue, and every successful sync re-validates approved write playbooks against the new schema (Chapter 9).
  • The resulting schema_table nodes are also what the query engines use to narrow a question to relevant tables (Chapter 8), and what documents link to.

  • Neighbours: one hop in either direction, paged. Traverse: recursive SQL common-table expression up to three hops, filterable by edge type.

  • Related documents: documents ranked by the canonical entities they share, weighting rarer entities more heavily; plus the list of entities two documents share.

GraphRAG

Cross-document retrieval rests on similar_to edges between chunks of different documents. A background link worker runs every five minutes over recently ingested projects (or on demand), finds each chunk's nearest cross-document neighbours, keeps up to 5 per chunk above a cosine similarity of 0.90, and writes them as edges. At query time the retriever seeds with the 10 most relevant chunks (using a raised HNSW ef_search of 400 so the chunk subset is not starved by post-filtering), expands one hop across similar_to, scores each neighbour by seed relevance × edge similarity, caps results per document, and can enrich the bundle with parent sections, shared-entity expansion and inline snippets.

8Natural-language data query

Agents ask questions of live databases in plain language. On this agent / API path the LLM never writes the SQL that runs: it produces a structured query plan which the server hardens, validates against the extracted schema and renders into parameterised, read-only SQL. The dashboard's chat modes are described at the end of the chapter.

Pipeline stages

  1. Plan cache. Plans are cached on the normalised question plus a fingerprint of the schema and prompt, so repeated questions skip the LLM and a schema change invalidates stale plans.
  2. Context. The planner builds a schema context from the extracted catalogue, adding categorical value hints sampled read-only from the source so filters use real literal values. When table embeddings are configured, the most relevant tables are selected by vector similarity.
  3. Plan. The LLM (chosen by the provider selector with failover) returns a JSON plan (tables, joins, filters, aggregations, grouping, having, ordering, limit) or asks for clarification.
  4. Harden and repair. Deterministic passes repair aliases, promote stray tables to joins, de-duplicate and validate join conditions, check every column against the extracted schema, cap ranked queries at 100 rows and correct ranking direction. A failed execution gets one simplification retry.
  5. Render. The SQL generator emits dialect-specific SQL with every value bound as a parameter; operators come from an allow-list and column, interval and sub-query shapes are accepted only through closed grammars.
  6. Execute and store. Results, status and the generated SQL are stored with the query record for the caller to fetch and for audit.

9Controlled writes LIVE

Writing to a customer database is off by default and, when enabled, runs through two narrow paths: a validated single-row insert, and named multi-step playbooks that must be approved before they can be executed. Every attempt is audited. The write path has so far been exercised at small volume.

Single-row insert

  1. Opt-in per data source: allow_writes defaults to false and is set by an administrator.
  2. Explicit table whitelist: an empty whitelist means nothing is writable.
  3. Validation against the extracted schema: required columns present, no unknown columns, type and length checks.
  4. Dedicated write connection with a 30-second timeout, used once.
  5. Audit of every attempt: successful, rejected and failed attempts all land in source_write_audit.

Agents discover what they may write with kg_describe_table (the column specification) before calling kg_insert_datasource_row.

Write playbooks

  • A playbook is a named, versioned JSON definition of inputs and steps, using a small template vocabulary ($input.*, $item.* with foreach, generated IDs, $now). It can express, for example, a header row with its detail lines.
  • Proposal is deterministic: the server derives a draft from header/detail table relationships in the schema, with no LLM involved.
  • Execution is atomic: all steps run inside one database transaction and roll back together on any failure.
  • Drift protection: after every successful schema sync, playbooks are re-validated and any that no longer match are marked stale.
  • Roles: for user-linked keys, approve, disable and delete require project admin and execute requires developer. Extending these role checks to keys not linked to a user is a hardening item before production (Document 03, Chapter 8).

Write paths currently support PostgreSQL sources. Both MCP write tools carry no read-only hint, so clients can ask the user to confirm, and read-only bridge tokens cannot call them.

Writes into the graph follow the same review discipline: agents submit knowledge as drafts (kg_ingest_node, or kg_ingest_batch for up to 50), which are approved singly or in bulk and then processed into nodes.

10Entity resolution & master records LIVE

Documents mention the same person, company or place in many spellings. A two-pass pipeline extracts typed entities per chunk and then decides, through progressively more expensive stages, which ones are the same, recording every decision before anything is merged.

Pass 1: extraction

Extraction is started per document through the API. The server first estimates the cost (chunks × average tokens × model rates × gleaning rounds) and refuses runs that would exceed the configured ceilings ($5 per run, $1 per document); chunks already extracted at the same content hash are skipped. Each chunk is then queued as its own job. The LLM returns entities of eight types (person, organisation, concept, event, location, artifact, document reference, project) and relations from a closed vocabulary (works_for, part_of, mentions, causes, related_to, derived_from, evidence), keeping names in the original language. A gleaning pass (at most 2 rounds) runs only on long, entity-sparse chunks and stops as soon as a round finds nothing new. Every entity keeps its provenance: source document, chunk and sentence span.

Applying merges

  • Suggestions are applied only when the server's apply_mode is apply; it is currently configured on. The check is a literal comparison, so any other value fails closed.
  • Hub guard: a pair where either node has 10 or more connections is never auto-merged; it goes to human review.
  • Merge is one transaction: follow the merged_into chain to the live canonical, union aliases and provenance, re-point edges without loss, supersede the member node, append a resolution-audit entry and write with optimistic locking. Every change is stamped with a merge-operation ID, so un-merge restores the exact prior state.
Measured quality (internal benchmark)Before auto-apply was switched on, the deployed three-stage pipeline was gated against a small internal Vietnamese benchmark (30 entity groups, 86 duplicate pairs; measured June 2026). Results: merge precision 1.000 and recall 0.915, with zero false positives. This is a small, domain-specific benchmark and should not be read as production accuracy on other corpora.

Master and derived records

The surviving canonical node of a merge acts as the master record for that entity (it keeps its entity type): it carries the unioned aliases, full provenance back to every source sentence, and an audit history of each merge. Separately, external systems can write derived records (summaries or reference records they own) back into the graph idempotently, link them to their evidence documents, fetch the latest one (kg_get_master_record) and revoke them.

12MCP bridge LIVE

The bridge is DAAB's integration surface for AI agents. It advertises 55 tools over the Model Context Protocol, 53 of them wired to the API (two have no server route yet), and maps each tool call onto the REST API, so agents get exactly the validation, authorisation and audit that the dashboard gets.

Transports and deployment

  • stdio (default): a single local client launches kg-bridge serve as a subprocess.
  • Streamable HTTP (serve --http): a shared network endpoint built on the official MCP Go SDK, with a per-session server instance. Health and readiness probes sit outside authentication. The bridge ships in the same image as the API server.

Authentication modes

ModeBehaviour
Passthrough (multi-tenant)Each request's bearer token is the caller's own DAAB API key. The bridge builds a per-session API client with that key, so the server enforces that key's role and project scope. One bridge serves many consumers, each scoped to the projects its key grants (see Chapter 3 for how project scope is enforced). Keys are issued in the dashboard with a role and a project scope.
Gate token (single-tenant)Callers present a bridge token (at least 32 bytes, or 43 characters, long, checked at start-up); an optional second token grants a read-only scope under which every write-class tool and local-execution tool is refused. The bridge calls the API with its own service key.

The HTTP middleware chain is: panic recovery → 60-second request timeout → authentication → rate limit (120 calls per 60 seconds per identity) → call log → MCP dispatch. Write-class tools are published without the MCP readOnlyHint annotation, so compliant clients ask the user before invoking them. An optional start-up switch makes the bridge refuse any non-loopback address, for deployments that require TLS to be terminated by a fronting proxy.

Per-call pipeline

  1. Scope check: under a read-only token, write-class and local-execution tools are refused.
  2. Misroute recovery: calls that clearly belong to another tool (for example, a natural-language question with a data-source ID sent to the structured-query tool) are rerouted, or answered with a corrective error that tells the model which tool to use.
  3. Project pinning: when the bridge is configured with a default project, it overwrites any project ID the model supplies (with a log entry). This protects against a model mis-addressing a call; it is not the tenancy boundary. Access is governed by the API key on the call, as enforced by the API (Chapter 3).
  4. Schema validation at the bridge (UUID patterns, enums, bounds), then mapping to the HTTP method, path, query and body; the result is rendered as MCP text content.

Delivery semantics

Lists are FIFO, and a pop removes the message, so delivery is at most once. Resilience is built into the jobs: each handler isolates failures per item (per draft, per document, per file), reports failures back to the API so they are visible in the dashboard, and never marks a failed item complete. Server-side, a heartbeat monitor fails schema-sync jobs that have been idle for more than 30 minutes, so nothing appears to run forever. A recovery sweep that re-publishes stalled extraction runs is implemented but not yet scheduled PLANNED. Workers shut down gracefully on SIGTERM.
