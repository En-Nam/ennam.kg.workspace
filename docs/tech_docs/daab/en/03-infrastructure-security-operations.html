1Deployment topology

DAAB is pre-production. It runs today as a self-hosted Docker Compose stack for development and demonstrations, using either a source-built development profile or a pinned-image release bundle (v1.0.0). A separate cloud dev environment on AWS runs the platform on managed services (ECS, RDS PostgreSQL, ElastiCache Redis, ALB), and CI/CD builds and deploys the Go service to it.

1.1 Self-hosted Docker Compose stack

The platform runs on a single Docker host with one private bridge network and seven services: PostgreSQL 16 with pgvector, Redis 7, the Go API server, the Python indexer and worker, the Next.js dashboard, and the MCP bridge (the Go image with a different entry point).

Two Compose profiles exist. The development profile builds from source, with hot reload for the Go server and bind-mounted repositories for code indexing. 1.2 AWS cloud dev environment

The repository's Terraform (deploy/terraform) defines modules for the VPC, security groups, RDS, ECS (with load balancer, image registry, autoscaling and alarms), secrets and a configuration bucket, with staging and production profiles. The ECS module defines one service, the Go API server. The managed Redis (ElastiCache) instance and the Python and dashboard tasks used by the cloud dev environment are not defined in the repository's Terraform. They are shown dashed in Figure 2.

Network and compute (Terraform)

  • VPC with public, private and database subnet tiers, and a NAT gateway for outbound traffic from the private tier.
  • Security groups allow the chain ALB → ECS → RDS only. RDS accepts traffic from the ECS security group and an optional bastion.
  • The ALB has an HTTPS listener with the ELBSecurityPolicy-TLS13-1-2-2021-06 policy, and HTTP is redirected to HTTPS when a certificate is configured. The health check calls /healthz.
  • ECS runs on Fargate with no public IPs. Deployments use a circuit breaker with automatic rollback. The staging profile can run on Fargate Spot.

Data, secrets and telemetry (Terraform)

  • RDS PostgreSQL 16 has encrypted storage and no public access. Slow-query logging, a statement timeout and pg_stat_statements are set through the parameter group.
  • The database password is generated into Secrets Manager and injected into the task. SSM parameters for runtime tuning and feature flags are provisioned, but the application does not yet read them (its cloud secrets provider is a stub).
  • The configuration bucket on S3 is versioned, encrypted and blocks public access. The deploy workflow publishes configuration files to it; the application does not yet read configuration from S3.
  • The credential-encryption key (KG_ENCRYPTION_KEY) is not supplied by the Terraform or the deploy workflows and is provided separately. Without it, the server starts with the encrypted-credential features disabled (Chapter 3).
  • CloudWatch receives the log group and alarms on CPU, unhealthy hosts, HTTP 5xx, application error rate and p99 latency.

2.2 Release bundle

Releases are produced as a pinned-image bundle: three images tagged with commit SHA, semantic version and latest, plus docker-compose.release.yml. A local release script builds and tags the images and can push them to a private registry. The Compose file takes an optional registry prefix and release tag, so the same bundle can be installed from any registry.

2.3 Database migrations

  • 86 versioned SQL migrations, each an up/down pair managed by golang-migrate, create 54 application tables. They cover the PostgreSQL extensions (uuid-ossp, pg_trgm, vector, unaccent), the knowledge graph, access control, data-source metadata, ingestion, entity resolution and agent memory.
  • Migrations are version-tracked and idempotent. The selfhosted and development profiles migrate automatically on start-up, and a restart is a no-op.
  • A dedicated kg-migrate CLI supports up, down, version, force and steps. It is used for operator-controlled changes and runs from source (Makefile); it is not included in the container images.
  • Automatic migration is disabled in the cloud profiles. The CI pipeline's migration step does not yet perform the migration (see §8), so cloud schema changes are currently applied by an operator.

3Configuration

3.1 Configuration layers (Go service)

The Go service resolves configuration in four layers. Each layer overrides the previous one:

  1. config/config.yaml: the domain model. It defines node-type schemas, the edge whitelist (59 rules), completeness rules, search, AI provider strategy and budgets, extraction cost ceilings, and entity-resolution gates.
  2. config/environments/<env>.yaml: one file per deployment profile (development, staging, production, selfhosted). Each sets server timeouts, the connection pool, logging, queue provider, metrics and feature flags.
  3. Environment variables prefixed KG_. In the cloud, the database password is injected into the task environment from Secrets Manager; the encryption key is supplied separately (§1.2).
  4. system_settings table: runtime overrides that administrators edit in the dashboard, cached in-process.

The Python services use typed pydantic-settings with defaults; the dashboard reads a few server-side variables plus build-time public identity-provider settings.

4Scalability

The request-serving tiers are stateless and can scale horizontally behind a load balancer. PostgreSQL is the single stateful core. Asynchronous work goes through Redis list queues to a separately scalable worker tier. No throughput or concurrency figures have been measured under production load, and none are claimed here.

4.1 What scales horizontally

  • kg-server (Go), stateless. All state is in PostgreSQL. Authentication is a per-request hashed key lookup, with no server-side sessions. The Terraform ECS profile autoscales on CPU, memory and requests per target (staging 1–3 tasks; production profile 2–10).
  • kg-bridge, dashboard BFF and Python indexer, stateless. The bridge builds a per-session MCP server and carries credentials on every request. The dashboard session is an encrypted cookie held by the browser. The indexer loads its embedding model once per process.
  • Python worker, stateless. Several workers can consume the same Redis lists. BRPOP hands each message to exactly one consumer.
  • PostgreSQL, stateful. Scales vertically. The RDS profile supports storage autoscaling and Multi-AZ. Logical replication is enabled in the parameter group for future read-replica or change-data-capture use.

4.2 Worker queue model

The Go server publishes JSON job messages to four Redis lists with LPUSH, and the Python worker consumes them with a blocking BRPOP in first-in, first-out order. The four lists carry code-repository indexing (ennam-kg:indexing); document drafts, uploaded-file extraction and connector synchronisation (ennam:kg_generation); chunk-level entity extraction and resolution (ennam:extraction, the only list with configurable parallel consumers); and agent-memory embedding (ennam:agent_context_embed).

Long-running synchronous operations are isolated from the request path. Schema synchronisation runs on an in-process job engine with 3 workers, 3 retries and a 30 s backoff. Natural-language queries are submitted asynchronously and long-polled. Chat responses stream over Server-Sent Events, with at most 3 concurrent chat streams per user.

4.3 Database and vector indexes

  • Graph storage uses a single node table with a type discriminator and JSONB properties. Properties have a GIN index, titles have a trigram GIN index, and there is a weighted full-text tsvector. Every update appends a history row in a separate table. Graph traversals are bounded recursive CTEs (depth ≤ 3).
  • Vector search uses three pgvector columns:
    • node and chunk embeddings, vector(384) with an HNSW cosine index;
    • agent-memory embeddings, vector(384) with an HNSW index;
    • table-description embeddings, vector(1536) with an IVFFlat index.
    Hybrid search runs the lexical and vector arms concurrently and fuses the results with Reciprocal Rank Fusion. There is no separate vector database to operate, secure or back up.
  • Connection pooling is configured per profile (for example 25 open and 10 idle connections in selfhosted). Queries against customer databases use a fresh, single-connection pool per query, so a slow customer database cannot exhaust the platform's own pool.

5Security architecture

Requests reach platform data through three entry points: the dashboard BFF, the MCP bridge, and the REST API called directly with an API key. All three converge on the Go API, which authorizes access to platform data; the realtime progress routes are the exception (§8, item 7). Customer database credentials are encrypted at rest. On the API and MCP query path, AI models never execute SQL directly: they produce a structured plan that deterministic code turns into parameterized, read-only SQL. Dashboard chat is handled differently: the Python indexer connects to the customer database itself (§5.5).

5.2 Authentication

  • API keys LIVE. Keys come from a cryptographic random source, and only a SHA-256 hash and a short display prefix are stored; the plaintext is shown once. Each key has a role, an optional project scope, revocation and last-use tracking. Every /api/v1 route requires a key except the two login endpoints.
  • Password login LIVE. Passwords are bcrypt hashes, and unknown users take a timing-equalised path. Accounts lock after 5 failed attempts, with administrator unlock, and a password change can be forced. Each password login mints a per-user session key and revokes the previous one, which enforces a single active dashboard session.
  • Dashboard session LIVE. An iron-session encrypted cookie (httpOnly, SameSite=lax, secure in production) carries the user's key only inside the encrypted cookie, so browser script never sees an API key. When the key is revoked upstream, the cookie is destroyed.
  • Single sign-on BUILT. Optional. Identity-provider JWTs are verified against a cached JWKS, with issuer and audience checks. Users are provisioned just in time as viewers; administrators are set by configuration.
  • MCP bridge LIVE. Two modes:
    • gate-token: a shared token that must be at least 32 bytes long (decoded hex or base64url) or 43 characters, checked at start-up. An optional second token grants a read-only scope.
    • passthrough (multi-tenant): each caller presents its own DAAB API key, which is forwarded per request, so the API enforces that caller's role and projects.
    The bridge does not terminate TLS. It warns on non-loopback binds, and refuses to start without TLS when KG_MCP_REQUIRE_TLS=true.
  • AI account linking BUILT. OAuth with PKCE. Tokens are encrypted at rest and refreshed by a background worker.

5.3 Authorization

  • Roles. Keys carry admin, developer, agent or viewer. Project membership carries admin, developer or viewer, with an additive hierarchy.
  • Project resolution middleware resolves the effective project for every /api/ request from the key's default, its project list or the user's memberships. It enforces an explicit override permission and blocks all mutations on archived projects.
  • Handler-level checks re-verify project access for identifiers passed in request bodies and on project-scoped routes; several by-ID read routes (node history, document outline and backlinks) also verify the resource's project. Writes to nodes, edges, data sources, source writes and connectors require a minimum project role for user-linked keys.
  • MCP read-only scope is enforced per tool at dispatch. Tools are classified read or write, and write tools carry no read-only hint, so compliant MCP clients show a confirmation prompt before calling them.
  • Applying a per-project check uniformly on every by-ID read, and to service and agent keys that are not linked to a user, is a hardening item (Chapter 8, item 4).
  • Project pinning in the bridge overrides model-supplied project identifiers. It protects against model mistakes but is not the tenancy boundary; tenancy is enforced by the API key's scope.

5.4 Credential encryption

Customer database connection strings, AI provider API keys, OAuth tokens and connector credentials are encrypted with AES-256-GCM. The server uses a 32-byte key supplied at runtime, generates a fresh random 12-byte nonce for every encryption, and stores nonce ‖ ciphertext ‖ tag, so any tampering is detected. Decryption happens only in memory, at the moment a connection is opened. The dashboard's chat mode forwards the still-encrypted connection string to the Python service, which holds the same key. For dashboard chat, the server also passes the selected AI provider's key to the Python service in a request header over the internal network, and the Python service calls the provider directly. Consolidating key custody and authenticating internal service calls are listed in §8.

5.5 Safe query design

The natural-language query pipeline behind the API and MCP tool kg_query_datasource is built so that the model never writes executable SQL:

  end
  s1 --> s2 --> s3
Figure 4. Guard pipeline for natural-language queries over customer databases (API and MCP path).
  • Plan, not SQL. The model emits a typed QueryPlan (tables, joins, filters, aggregations, grouping, ordering, limit). All values become bound parameters. Operators must be on an allow-list, and the few permitted expression shapes (intervals, scalar sub-queries) must match closed grammars.
  • Schema grounding. Plans are repaired and validated against the extracted schema: column existence, join promotion and de-duplication, ON-clause validity, and a cap of 100 on ranked queries. If execution fails, the pipeline makes one simplification retry.
  • Execution guards. The generated statement must start with SELECT or WITH. Each query uses a fresh single-connection pool. On PostgreSQL sources the session is additionally set to READ ONLY at the database level. MySQL, MariaDB and SQL Server rely on the deterministic generator and the statement-prefix check. A 30 s timeout and a 10,000-row hard cap (with a truncated flag) apply to all dialects.
  • Least privilege at source. Customers are advised to register read-only database credentials, the strongest guard and independent of DAAB.

Dashboard chat has two further modes, implemented in the Python indexer, which opens its own connection to the customer database (Figure 3). The fast mode uses the same plan-then-generate approach with bound values. The agentic mode lets the model compose SELECT statements inside a tool loop. These are checked by a statement validator (single statement, SELECT/WITH only, a blocklist of data-changing keywords, a length limit) and results are trimmed to 50 rows after execution and 20 rows per tool result. Neither Python mode sets a database-level read-only session. Tightening both is listed in §8.

5.6 Controlled writes

Writes to customer databases are off by default and pass four independent controls:

  1. Per-source opt-in. allow_writes is false until an administrator enables it.
  2. Table whitelist. Only listed tables are writable. An empty list means nothing is writable.
  3. Validation against extracted metadata: required and unknown columns, types and maximum lengths.
  4. Audit. Every attempt, whether successful, rejected or failed, is written to source_write_audit.

Multi-step writes are expressed as named, versioned playbooks. Playbooks are declarative server-side step definitions, proposed deterministically (no model involved) and approved by a project administrator. They execute in a single database transaction. After every schema sync, playbooks whose target schema has drifted are marked stale automatically. The write path currently supports PostgreSQL sources.

5.7 Audit logging

Security-relevant activity is recorded in dedicated tables: audit_trail (node creation, settings changes, schema syncs, query submissions); kg_audit_log (reads of conversation history); source_write_audit (every write attempt against a customer database); knowledge_node_versions (version history written by a database trigger on every update; graph edits only append versions, while regenerating a document replaces its sections and chunks together with their version rows); and ai_usage_logs with budget tables (per-request model usage and cost attribution). Administrators query the audit log and per-entity history through the API.

6Data protection & AI data flow

DAAB computes embeddings and reranking on local CPU models inside the deployment, so document content is never sent to a third party for embedding. External language models are called only for specific steps, and each step sees a bounded subset of data. All providers are configurable, including self-hosted OpenAI-compatible endpoints.

6.1 What stays local

Embeddings: document sections, chunks, entities and agent-memory records are embedded with intfloat/multilingual-e5-small (384 dimensions) on CPU in the Python service, and search queries are embedded by the same local service. Reranking: entity-resolution candidates are filtered by a local cross-encoder. OCR and parsing: Tesseract (including Vietnamese) and local layout OCR run in the worker, and temporary files from connector syncs are deleted after processing. Query execution: SQL runs from the DAAB deployment to the customer database, and results are stored only in DAAB's own database and returned to the caller.

When an AI agent calls DAAB through MCP, the results it receives are processed by the agent's own model, outside DAAB's boundary. Which data goes on to that model is governed by the scope of the key the agent holds.

6.3 Provider configuration

  • Provider registry. AI providers are registered in the database with encrypted credentials. The server routes each request through a priority-ordered selector with failover and a circuit breaker. Models can be assigned per function, such as planning, extraction or verification.
  • Supported interfaces: the Anthropic API, a linked Claude subscription (OAuth), and any OpenAI-compatible endpoint. The second option allows a customer to point DAAB at a regional provider or a self-hosted model server, so that no data leaves their environment.
  • Cost controls. Extraction runs are estimated before they start and refused above per-run and per-document ceilings. Every request proxied through the server's AI layer carries a request type and run identifier for cost attribution. Two paths call providers directly and are not recorded in that usage log or covered by its circuit breaker: an optional direct extraction endpoint (EXTRACTION_LLM_URL) used for chunk-level extraction, verification and adjudication, and dashboard chat in the Python service. Plan caching and an empty-result fast path avoid unnecessary calls.
  • Data-processing terms with each external provider depend on the customer's deployment choice: TO BE COMPLETED

7Operations

7.1 Logging and metrics

  • Structured logs. The Go service uses log/slog (JSON in production-like profiles) with a request-ID middleware, access logging and panic recovery. Request bodies are not logged in those profiles.
  • CloudWatch (optional). Logs can be shipped to CloudWatch Logs in batches with a configurable retention, and an in-process metrics collector can publish to CloudWatch Metrics every 60 s. The self-hosted profile writes to standard output only, and ECS collects container output into its log group.
  • Alarms (Terraform). CPU, unhealthy targets, HTTP 5xx, application error rate and p99 latency.
  • Python services log through the standard library at a configurable level. Per-item failures in the ingestion pipeline are logged at warning level or above, never swallowed silently.

7.2 Health endpoints

kg-server, kg-bridge and the Python indexer each expose GET /healthz (liveness) and GET /readyz (readiness), outside authentication. Readiness checks the dependencies each service needs: the database ping for kg-server (503 when unavailable), the API for the bridge, and the API and Redis for the indexer. The indexer reports a failed dependency as degraded in the response body but still returns HTTP 200, so orchestrators cannot yet use it to hold back traffic. PostgreSQL and Redis use Compose health checks (pg_isready, redis-cli ping), and application services wait until these are healthy. The ALB target group uses /healthz.
