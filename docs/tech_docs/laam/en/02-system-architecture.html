1Overview and design principles

LAAM is a self-hosted, multi-user AI work assistant. People ask business questions in chat or by voice; LAAM answers them against live data by calling tools on connected systems. In chat, every write to a connected system waits for the user to confirm a code-built preview; scheduled workflows may write only through tools marked workflow-safe and only to allow-listed recipients. The same tool layer powers durable, schedulable workflow graphs that an AI can author and test-run on the user's behalf.

LAAM is a single Next.js 16 application (React 19, TypeScript strict) backed by PostgreSQL 16. It ships seven product surfaces:

SurfaceWhat it doesStatus
Chat /chatMulti-provider LLM assistant with tool calling over connectors and MCP servers, write-confirm cards, file attachments (PDF, DOCX, images, OCR), rich rendering (tables, charts, maps) and per-user workspaces with a shared persona.LIVE
Voice /constellationFull-screen, hands-free voice command centre: browser speech recognition, voice-activity barge-in, streaming neural text-to-speech from a self-hosted service.LIVE
Workflows /workflowsDurable graph automations (agent, connector, MCP, condition, for-each nodes; optional parallel execution), cron schedules, dry-run, and AI authoring that test-runs the graphs it proposes. The workflow engine is LIVE; the cron scheduler and AI authoring are BUILT.LIVE / BUILT

Design principles

Five principles recur through the code and explain most of the architecture described in later chapters. Each is backed by code or tests rather than by convention alone.

PrincipleHow it is enforced
Use the model only for judgementRouting, retries, extraction, arithmetic, table building and write execution are done by code. The model decides which tool to call and how to phrase the answer. Example: result tables are built from the tool's rows by code and streamed as a separate frame, so the model never retypes numbers.
Human confirms writes in chatA tool counts as a read only when it is declared read-only by a built-in connector, or by an MCP server the user has marked trusted; everything else is treated as a write. In chat, every write to a connected system suspends the turn and waits for the user to confirm a code-built preview; the confirmed call runs in code with the sealed arguments, and its nonce is checked against the audit log. Scheduled and unattended workflows may execute writes only for tools marked workflow-safe and only to allow-listed recipients; all other writes fail closed.
Fail loudNo silent provider fallback, no blank replies, no "success" without an executed write. Each failure path produces a coded, tri-lingual notice or a failed step that names the cause.
Model-provider-agnosticFive providers sit behind one internal adapter contract. Chat users pick a model; background tasks resolve one through a deterministic router. Capabilities (tools, vision, structured output) are checked per provider.
Connector-agnosticExternal systems plug in through a generic Connector interface or as user-added MCP servers, and the integration layer is generic. Connector-specific behaviour (for example list-to-detail drill-down pairs) is supplied through configuration. A few model-facing prompt strings still reference one knowledge-graph server's tools; their cleanup is tracked.
No code execution by the agentA test in the unit suite fails if process spawning, eval, new Function or the vm module appear anywhere in the agent or workflow engines; there is no CI yet, so the suite is run by hand. The internal tools and the workflow node kinds are fixed in code, and the test also checks tool names and count. The assistant can only act through declared tools.

Deployment shape

The reference deployment is a Docker Compose stack on a single GPU-equipped host: the LAAM application container (multi-stage node:24-alpine image, Next.js standalone output, non-root user, health check; OCR and PDF binaries bundled), the TTS service, SearXNG and a database admin UI. PostgreSQL 16 is an external instance shared with other services on the host network. Ollama and a small host-metrics agent run natively on the host so they can reach the GPU. Ingress is through a private mesh-VPN, optionally published to the internet through the same VPN's tunnel feature. Infrastructure, security and operations are covered in document 03 of this pack.

4Chat and agent engine

A chat turn is one POST /api/chat request. The route authenticates the caller, assembles context, runs a tool loop against the chosen model, and streams the answer back while persisting every message and tool call. The same engine serves the voice surface, which only switches the output guide.

4.1 Turn lifecycle

The route performs these steps in order:

  1. Authorise. Require a session, then require a mutating role (viewers are read-only). Before any I/O, Claude model ids are checked against an allow-list (400 otherwise); BytePlus and Cerebras ids are recognised by list, and any other id goes to the local runtime.
  2. Validate. Reject empty messages, strip NUL bytes, cap images at two per turn and about 2.8 MB (base64) each.
  3. Load context. Load or create the conversation. A new conversation is stamped with its workspace after an ownership check; the workspace never changes afterwards.
  4. Budget history. Replay history within a provider-aware character budget. Overflow is folded into a rolling summary by the internal model (chapter 5) and stored on the conversation row.
  5. Build the tool surface. Internal tools, plus the user's connected built-in connector tools, plus every tool from the user's MCP servers, namespaced per server (chapter 6).
  6. Pre-dispatch a quick tool (optional). If the user picked a specific tool in the UI, code runs it deterministically before the model loop, through the same safety gate.
  7. Assemble the system prompt (section 4.2), then add proactive alerts (stuck or expensive monitored sessions, de-duplicated per conversation with a 6-hour cooldown) as a separate frame, never inside model prose.
  8. Run the tool loop (section 4.3), then the final completion (section 4.6).
  9. Finalise. Strip leaked tool-call JSON, persist the assistant message with token counts, persist every tool call and result, emit trailing frames.
  10. Or suspend. If the model proposed a write, the turn ends with a confirm card instead (chapter 7).

4.2 System prompt and persona precedence

The system prompt is assembled by code from six parts in a fixed order: base persona, today's date, a language hint (Vietnamese, English or Chinese), the tool block (only when tools exist), each MCP server's own instructions (captured from its initialize response, capped), and an output guide. The text guide teaches the table, chart and map block contract; the voice guide sets a spoken register, forbids reading identifiers aloud and allows at most one table or chart.

The tool block carries measured behavioural rules, phrased generically: a write must go through a tool and success must never be claimed without one; "search again" forces a fresh call; counts come from structured data; multi-metric comparisons are split into separate calls; natural-language data tools receive the user's own wording; SQL is never placed in a natural-language field.

PrioritySourceEffect
1Explicit system-prompt overrideReplaces the entire prompt; tool, date and language blocks and proactive alerts are dropped. Used for power users and internal paths.
2Workspace personaReplaces only the base persona; tool, date and language blocks remain. Resolved server-side from the conversation row, so a voice turn resumed elsewhere gets the same persona.
3Custom agent selected by the userReplaces only the base persona.
4System defaultBuilt-in assistant persona.

A workspace persona is either a custom agent or free-text instructions, never both (the API rejects both with 400). A deleted custom agent falls back to the default and the UI shows a warning badge.

4.3 The tool loop

runToolRounds (lib/agent/orchestrator.ts) runs until the model stops calling tools. It replaced a fixed four-round cap in release 2.5.0, which had cut off any task needing more than three tool rounds (for example, summarising ten emails and then sending a report).

MechanismBehaviour
Runaway backstop25 rounds by default (configurable, hard ceiling 50). The last round is forced to text.
Repeat guardThe same tool with identical arguments three times is treated as stuck (eight times for status-polling tools). The loop stops dispatching and tells the model to answer with what it has. "Stuck" and "out of rounds" are reported separately for operator tuning.
Context evictionWhen the accumulated conversation exceeds a character budget (about 37k characters for local models, about 400k for cloud), the oldest tool results are replaced by a stub, keeping the three most recent. This follows the tool-result clearing pattern used by major model vendors.
Per-result processingEach result is unwrapped, checked for emptiness, turned into a data panel if tabular, and annotated so the model does not retype a table already on screen (chapter 6).
One-shot nudgesAt most once per turn each: read a page after a web search returned URLs; re-ask when the model answered from memory in round 0 despite having tools; stop using LAAM's own audit log for business questions. Workflow agent nodes disable nudges because their prompt is the instruction.

4.4 Streaming protocol

A chat response is a text/plain stream, not Server-Sent Events. Plain answer text is interleaved with JSON control frames delimited by the ASCII record separator (U+001E), which never occurs in normal prose. The conversation id travels in a response header. Workflow runs, by contrast, publish over the SSE bus at /api/events.

FramePurpose
toolA tool call started or returned (live trace in the UI).
viewA code-built data panel (table, optional chart hint) derived from a tool result.
citeSources used by the answer.
pending_writeA write awaiting human confirmation: code-built preview and sealed token.
proactiveAlerts about stuck or costly monitored sessions.
tokensToken usage, sent only when the provider actually reported usage (no fabricated zero cost).
hbHeartbeat while a reasoning model is thinking, so idle proxies do not drop the connection.

4.5 Reasoning effort by phase

For reasoning models on BytePlus and Cerebras, LAAM sets reasoning effort separately for tool rounds and for the final answer (each falls back to a shared setting; only low, medium and high are forwarded). This lets a deployment trade latency against depth where it matters. The shipped example configuration sets the final phase to low and deliberately leaves tool rounds at the provider default: low effort during tool selection produced a wrong "nothing found" answer on a data-lookup question in testing. DeepSeek has its own settings, and its "thinking" mode is disabled on tool rounds after a traced 100-second-plus call.

4.6 Final answer and context management

  • Digest before the final completion. Large tabular results reach the model as a digest (row count, columns, code-computed per-column totals across all rows, a few sample rows). The raw rows stay in chat_tool_call, so a reloaded conversation rebuilds its tables exactly.
  • Question pin. After a tool-using turn on the cloud (BytePlus or Cerebras) path, the user's question is restated before the final completion. It was added after a measured case where the answer drifted to an earlier topic.
  • Empty-answer recovery. If a cloud model's final stream is empty, the engine retries exactly once with an "answer now from what you have" nudge; if still empty, it sends a coded notice. A blank bubble is never shown.
  • Rolling summary. LAAM has no separate long-term memory store. Conversation memory is the rolling summary on the conversation row plus the persisted tool turns. Any shared memory a customer wants comes through a connected MCP server like any other tool.

Routing rules

  • Cloud-first default. The chat picker preselects BytePlus if configured, then Cerebras, else the local model. A deployment without cloud keys runs entirely on local models.
  • No silent cross-provider fallback. A provider error produces a coded, tri-lingual notice (authentication, rate limit, overloaded, connection, API) and the turn is persisted. BytePlus and Cerebras retry once on 429, 503 or 529 after a configurable delay.
  • Three internal entry points. callModelText (no tools), callModelChat (tool loop) and callModelGenerate (structured JSON).
  • Capability checks. Claude can summarise but cannot run a workflow agent node; the run fails at that node with an explicit error rather than producing an untooled answer.

Structured output per provider

Workflow authoring needs reliable JSON. Support differs by provider and model, so the strategy is chosen per provider from measurements: JSON mode where supported; prompt-only JSON when a model rejects the response_format parameter; a forced tool call ("structured tool") as the default for branch derivation on BytePlus gpt-oss-120b (10 of 10 in testing); strict JSON schema on Cerebras. DeepSeek's strict function calling measured worse and is opt-in only.

Cost accounting

A pricing table (USD per million input and output tokens) covers Claude, BytePlus, Cerebras and DeepSeek models. An unmatched model is costed at a default Sonnet-level estimate; models whose price is not published show no cost rather than a guess. Tokens are recorded per chat message and per workflow step together with the model that actually answered, and cost is derived at write time. Monitoring shows model, tools and cost for chat and workflow runs alongside monitored agent sessions.

Everything the assistant can do is a tool. Tools come from three sources: a closed set of internal tools, the built-in connectors a user has connected, and the MCP servers a user has added. All three share one dispatch path and one safety gate.

6.2 Built-in connectors

Each built-in connector implements the same Connector interface: an id, an auth mode, and a list of tools that each declare kind: "read" | "write" and whether they are safe to run unattended in a workflow. Credentials are encrypted per user (AES-256-GCM with a key derived per user by HKDF-SHA256). OAuth token refresh runs at the single execute() chokepoint under a Postgres advisory lock, because several providers rotate single-use refresh tokens; a revoked grant flips the connector to "needs reconnect".

6.3 MCP client — the generic integration path

Any system that speaks the Model Context Protocol can be added by a user at runtime: a database gateway, a knowledge-graph server, a SaaS vendor's MCP endpoint. The MCP path is generic; a few model-facing strings still name one knowledge-graph server's tools (cleanup tracked). Server configuration (URL, bearer token, headers) is stored in the same encrypted per-user credential table as built-in connectors.

PropertyImplementation and rationale
TransportsStreamable HTTP first, one retry over SSE for older servers. Connections are per operation and always closed.
SSRF guardAt connect time the server URL's hostname is resolved and every resulting address is checked against private, link-local, metadata, IPv6 unique-local and IPv4-mapped ranges before a transport opens. Hardening item before production: one DNS-pinned guard for all outbound fetches, adding the carrier-grade NAT range and a re-check on redirect.
NamespacingEach tool is exposed to the model as mcp__<server>__<tool>, so servers cannot collide with each other or shadow built-ins. Server slugs stay stable when a server is renamed or re-pointed.
Prefix de-collisionWhen one tool name is a strict prefix of another on the same server, the shorter name is padded. Measured on one provider: the longer tool was reached 0 of 6 times before the fix and 6 of 6 after; on one 49-tool server it made 11 tools reachable.
Server instructionsEach server's initialize instructions are captured and placed in the system prompt, so scoping information a server publishes is not re-derived with extra list calls on every question.
Limits200 tools per server (logged truncation), 15-second call timeout, error text to the model capped at 300 characters, 200k-character raw backstop with a visible truncation marker; per-result shaping to 8k characters (local) or 120k (cloud).
In-band errorsMCP's isError flag is carried through: the workflow runtime fail-stops on it and AI authoring discards such observations.

6.4 Result handling: code-built tables and digests

MCP results arrive as text containing JSON, while internal tools return objects. A single unwrapping function normalises both, and every shape-inspecting step uses it; a guard that skipped it would silently never fire.

  • Data panels. When a result is tabular (at least 3 rows and 2 columns with a consistent key set, up to 500 rows), code builds a table and streams it as a view frame; a chart hint is added for up to 25 rows. The model is then told the table is on screen. The motivation was measured: on 13 test questions, only 2 results met the old size threshold for a panel; in the other 11, the numbers on screen were the model retyping the result, and it introduced errors (a truncated product name, a spurious space in an identifier, a lost cell and a repeated row).
  • Digests for the model. Large results reach the model as counts, columns, code-computed totals and sample rows. In one measured case a 62-row result took 103 seconds and 3,225 output tokens to retype, with errors; the digest removes that cost.
  • Formatting rules. Markdown tables are repaired by code; numbers use thousand separators and explicit currency units.

7Reliability guards

Language models confabulate, pick near-miss tools and give up early. LAAM does not rely on prompting alone to prevent this. Each failure mode observed in testing has a structural guard in code, triggered by observable facts (a missing tool call, an empty result, a malformed name) rather than by classifying the user's intent.

7.1 Write confirmation round-trip

The write gate is the most important guard. Every dispatch passes through withSafety, which classifies the tool from its own declaration. Unknown tools are treated as writes. In chat, an unconfirmed write never executes: it raises a signal that the route turns into a suspended turn.

Three design choices matter here. The preview shown to the user is built by code from the arguments, never from model prose, so the user approves what will actually be sent. The token is stateless (sealed with authenticated encryption) and carries the original model, so the narration after confirmation continues in the same voice. And the token's nonce is checked against the audit log before dispatch, so a confirm that has already been recorded is rejected. Hardening item before production: an atomic nonce claim and idempotent retry for confirmed MCP writes.

8Workflow engine

A workflow is a JSON graph of typed nodes stored per user. It can be run on demand, on a cron schedule, or as a dry-run test. Runs are journaled step by step so they survive a process restart, and writes are recorded in an idempotency ledger so a resumed run never sends twice.

8.1 Graph model

Node kindBehaviour
agentRuns the tool loop with LAAM's internal read tools only, then one final call through the internal router. Optional custom-agent preset (a missing preset fails loudly) and optional output schema. An extract mode pulls a field from an earlier step in code, with no model call; it was added because model-based extraction was the entire cost of some runs (about 3 s per call against 24–55 ms MCP calls).
connectorCalls a built-in connector action with templated arguments ({{steps.x.output}}, {{trigger}}).
mcpCalls a tool on a user's MCP server. An optional pollUntil re-issues a status call until a field reaches a value; it is inferred by code from observed calls, never authored by the model.
conditionEvaluates a predicate (10 operators, combinable with all/any) and follows the true or false edge.
foreachRuns a sub-graph once per item with {{item}} and {{index}}, sequentially.

External data enters a workflow only through connector and MCP nodes. The node kinds are fixed in code. Budgets: 200 steps and 100 for-each items per run; in parallel mode, fan-out of at most 12 edges per node.

8.2 Execution modes

  • Linear (default): a recursive edge walker evaluates conditions, runs for-each bodies, shares one budget counter and stops at the first failure.
  • Parallel (per-graph flag): a topological DAG scheduler with fan-out and OR-join fan-in, multiple start nodes, and tri-state pruning of untaken branches. Two semaphores separate model-bound work (2 concurrent) from I/O (6 concurrent). Fail-stop, cancel and budget are cooperative: an abort flag, then a drain of in-flight nodes before finalising. A deadlock detector guards the scheduler, and a golden test proves that a linear graph at concurrency 1 produces a byte-identical run to the linear walker.
  • Validation uses Kahn's algorithm for cycle detection (a previous depth-first check falsely flagged diamond shapes), reachability across start nodes, and a family of lint rules that reject references a node cannot actually produce. The same validation gates Save.

8.3 Run lifecycle, durability and idempotent writes

  • Snapshot. The graph is copied onto the run row at start, so editing a workflow never changes a run in progress.
  • Journal. Each node writes a workflow_run_step row (input, capped output, tokens, cost and the model actually used) and publishes a step event with a 280-character output preview for the live canvas.
  • Idempotent writes. Before a write, the executor claims a row keyed on (run, node, iteration) with a unique constraint. After success the row is marked done with the output. On resume, a done write replays its stored output; a claimed-but-unrecorded write fails loudly instead of risking a duplicate email or message.
  • Crash resume. On boot, runs still marked running become resumable. The next scheduler tick claims up to 25 of them with FOR UPDATE SKIP LOCKED, rebuilds context from the journal and skips completed nodes.
  • Output gates. An agent node with an output schema is checked for missing required keys (a null counts as missing) and for type mismatches; it gets one self-repair attempt with the exact field names, then fails at that node. The type check exists because a presence-only check once let an empty result list pass and a run finished all-green on no data.
  • Recipient gate. Writes that leave the organisation (email, Slack, WhatsApp, Zalo) require every resolved recipient to be in that channel's allow-list; an empty allow-list blocks. The recipient parser rejects header injection.

9AI workflow authoring

BUILT Users can describe an automation in plain language and have LAAM build it. The authoring pipeline is trace-grounded: the model must first observe real tool calls on the user's own connectors, and it may only build a graph out of calls it has actually seen succeed. Code, not the model, compiles the final graph.

StageWhat it guarantees
ProbeThe model is shown parameter names but never real values, so it cannot copy a live identifier into a saved graph (an earlier bug did exactly that). Writes are blocked and recorded, never executed.
Plan DSLThe plan schema cannot express a tool name, connector id or literal argument value. Plan nodes reference observed calls by opaque ref and wire arguments to earlier steps.
planGuardRejects on the first failure, naming the real alternatives so the error doubles as the repair prompt: the ref must exist; argument keys must be real; values must be templated, not bare literals; sources must be grounded; extracted fields must exist in the observed payload; fan-out ≤12; no unused reads.
Data closurePulls in the producer calls a plan depends on, including calls from earlier turns of the authoring conversation. Without it, "the first item" was frozen to one specific item forever.
CompileHigh-entropy literals become step references; recipient and body arguments of writes are stripped and re-asserted as code-owned; parallelism is inferred.
MergeHuman-confirmed write nodes (id, arguments, recipient) stay invariant across rebuilds; hand-edited prompts are preserved when the step list only extends.
VerifyRuns the graph for real with mocked writes (40 steps, 2 for-each items, 60-second deadline) and badges failing nodes on the canvas.

Two authoring surfaces

  • One-shot generate (POST /api/workflows/generate): probe, plan, verify; the editor applies the result as an undoable proposal behind a confirm card, even if some nodes are red, so the user sees exactly what failed.
  • Multi-turn authoring panel (POST /api/workflows/generate/chat): each turn runs a write-blocked tool loop, then overlaps a prose reply with the plan build (saving a median 2.6 s per turn). A no-data gate refuses to paint a graph if no read actually resolved to an answer and asks a clarifying question instead. Only a verified green graph is offered, with up to three observed sample rows. Writes are appended in a separate, human-confirmed step. A test run executes the proposed graph as a draft run and digests the outcome back into the conversation with identifier-shaped values masked, so the model can react to real outcomes (for example add a branch for a "clarification needed" status) without hard-coding values.
  • Review (POST /api/workflows/review): a plain-language review of the graph currently in the editor.

10Voice pipeline

The voice surface is a full-screen command centre that runs the same chat engine hands-free. Custom agents sit on an inner ring and tool groups on an outer ring; disconnected connectors are dimmed. Speech in and out is streamed so that the assistant starts talking before the whole answer is synthesised.

  • Same engine, different guide. Voice turns use the chat route with mode: "voice". The voice guide asks for a spoken register without identifiers, and states that brevity must not reduce lookup depth. It targets a measured problem: 3 of 17 voice turns were shallow or fabricated, against 0 of 6 in text mode. In a 12-turn retest, no voice turn skipped tool calls; 2 were still shallow because the model chose the wrong tool, which the (flag-off) list-to-detail drill-down addresses.
  • Speech-to-text. A swappable provider interface; the first implementation is the browser's Web Speech API. A self-hosted Whisper provider is PLANNED.
  • Barge-in. Two gates: a voice-activity model served from LAAM itself, and a dynamic threshold tied to the current playback level so the assistant's own voice does not trigger an interruption.
  • Text-to-speech. A self-hosted VieNeu TTS service (Python, CPU) with a Vietnamese preset voice and a cloned English voice. The streaming endpoint pipes 48 kHz PCM unbuffered; sentence segmentation keeps every synthesis request well inside the route timeout regardless of answer length, and the next segment is fetched while the current one plays. The container's CPU cap is paired with matching thread limits; capping CPUs alone collapsed throughput. The browser's built-in speech synthesis is the fallback.
  • Display panel. The model may include at most one table or chart per voice answer; it is lifted out of the spoken text and shown on a non-modal panel. Result tables are collapsed by default on both chat and voice surfaces.

11Data model

LAAM stores everything in one PostgreSQL 16 database: 22 tables and one enum, managed by 19 versioned Drizzle migrations (migrations only; schema push is never used against real data). The model is a single organisation with roles, not multi-tenant; per-user data is isolated by foreign keys to user and ownership checks in every query.

Conventions

  • Ownership. Per-user resources are filtered by the caller's id in the query itself, so another user's record behaves as not found rather than forbidden.
  • Validation. Request bodies are validated with Zod or explicit parsers before any I/O; Claude model ids are checked against an allow-list.
  • Secrets never echoed. Credential and MCP-server responses mask secrets to their last four characters; tokens are shown once at creation.
  • Streaming. The chat turn streams framed text (chapter 4); live updates for sessions, workflow steps and notifications use SSE on /api/events, filtered per user.
  • MCP server. POST /api/mcp implements initialize, tools/list, tools/call and ping as hand-written JSON-RPC over Streamable HTTP, exposing only read-only tools. No connector write is reachable through it.

13Evaluation harness

Beyond unit tests, LAAM has an offline evaluation harness that runs the real system prompt and the real tool loop against real models, scores behaviour with automated graders, and records each run in the database for trend tracking.

Method

  • What is real. The production buildSystemPrompt and runToolRounds, and a live model from the configured provider (BytePlus, Cerebras or Ollama; a missing key fails rather than falling back).
  • What is stubbed. Tool dispatch. Tools return deterministic stub responses, so no connector or MCP server is called and runs are reproducible. Flag-off guards (drill-down) are not enabled.
  • Main suite. 17 scenarios across tool selection, arguments, restraint (not calling tools for small talk), rich rendering, write intent, termination, web research and utilities. Each scenario runs k times; 8 graders score 7 dimensions. Each run is stored in eval_run with the git SHA and shown on the Reliability page.
  • Scale suite. Measures tool-selection pass rate as the number of tools offered grows (4, 16, 32, 60), padding with a distractor pool drawn from the real tool union including a snapshot of a 48-tool MCP server, with Wilson 95% confidence intervals and no-call separated from wrong-call.

Latest measured results

Weak spots named by the scorecard: one scenario consistently prefers a digest tool over the expected statistics tool; one restraint scenario calls the wrong read tool; an open-ended web-research scenario runs 10–16 tool rounds before answering; one detail lookup terminates late. Grounding is the lowest dimension because the grader requires specific values from the stub to appear verbatim in the answer.

Scale suite, gpt-oss-120b: an early low-sample run (k = 3) suggested that tool selection stayed stable as the number of offered tools grew from 4 to 60; a later 60-tool run (k = 8, 2026-08-03) averaged 67%, so scaling is still being measured. At k = 16, the three highest-risk probes (voice-mode detail lookup, and two variants with a misleading earlier conversation) each passed 16 of 16, run without the drill-down safety net.

How to read these numbersThey are grader pass rates on scenarios with stubbed tool responses, not end-to-end accuracy on customer data. Real payloads are larger and noisier than stubs, and the harness does not exercise live connectors. The harness exists to catch regressions in prompt and loop behaviour when models, prompts or guards change, and to make those changes measurable.
