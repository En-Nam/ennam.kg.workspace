1Maturity summary

LAAM is a self-hosted, multi-user conversational AI work assistant (chat and voice). It answers business questions against live data and acts through connected systems. In chat, every write to a connected system waits for the user's confirmation of a code-built preview; scheduled workflows may write only through tools marked workflow-safe and only to allow-listed recipients. It also runs durable, scheduled automation workflows. Its core is implemented and in daily internal use. It is pre-production: there are no production customers yet.

1.3 Deployment status

LAAM is pre-production. It runs as a self-hosted Docker Compose stack: the application container, a self-hosted TTS service, a self-hosted metasearch service and a database admin UI, against an external PostgreSQL 16 instance. Local models are served by a native Ollama on a GPU host. The stack is used today for development, internal use and demonstrations. No uptime, SLA or load figures have been measured, and none are claimed.

3Engineering process & quality

The codebase is test-heavy and measurement-driven. Most behavioural guards in the agent loop cite the dated measurement that motivated them. Automated gates exist and pass on application code. What is missing is enforcement: there is no CI pipeline, so the gates are run by developers, not by the repository.

3.3 Change management and review

  • Branching. Work happens on task branches merged through pull requests (24 merged so far). There is a separate deploy branch. Commits mostly follow conventional prefixes (feat, fix, test …).
  • Design before code. Larger features carry a written specification and plan in the repository (39 specs, 69 plans). Plans state their success criteria, and each merge records how verification was done.
  • Release notes. A detailed changelog records, per change, the motivating measurement, the test delta and what was deliberately deferred.
  • Database migrations. Only committed migrations are applied (19 so far: 17 generated, 2 hand-authored). Schema push is never used against real data.
  • Not present: CI configuration, pre-commit hooks, branch-protection rules held in the repo, dependency-update automation, or container image scanning. Review is recorded in commit messages and pull requests, not enforced by tooling. These items are on the hardening roadmap (§5.1).

3.4 Offline evaluation harness

A separate harness runs the real system prompt and the real tool loop against real models. Tool responses are stubbed: no live connectors are called, and flag-off features stay off. Each scenario runs k times, and eight graders score tool selection, arguments, grounding, restraint, termination, write intent, rich-block rendering and source citation. Results are stored with the git SHA and charted on the in-app Reliability page.

Run of 2026-09-03 (internal QA record). Model: gpt-oss-120b via a cloud provider. k = 5 × 17 synthetic scenarios = 85 runs, all with stubbed tool responses.

Caveats — these are grader pass rates, not accuracy The scenarios are synthetic and the tool responses are stubbed, so these numbers are not end-to-end accuracy on customer data. The grounding grader checks that expected tokens appear in the answer. Its lowest scores come from scenarios where the model chose a different, plausible monitoring tool, and from one open-ended web-research scenario that ran 10–16 tool rounds.

A second suite measures tool selection against tool count. It uses 4, 16, 32 and 60 tools, where 60 is a measured real per-user tool surface of 12 internal tools plus 48 from one MCP server. It reports Wilson confidence intervals and separates "no call" from "wrong call". An early low-sample run (k = 3) suggested stable selection as tools grew; a later 60-tool run averaged 67%, so scaling is still being measured. At 60 tools the tool schema costs about 6k tokens per round, and a k = 16 re-run of the three highest-risk multi-step probes passed 16/16. These are stubbed-dispatch measurements for one model.

4Known limitations

These are the documented gaps at the baseline. None prevents internal use and demonstrations. Items marked as hardening are pre-production work, and §5.1 lists them.

4.1 Platform and operations

AreaLimitation
Single-process designThe live event bus, the login/registration rate limiters and workflow resume all assume one application process. Horizontal scale-out needs a shared bus and limiter store.
Scheduler triggerSchedules fire only when an external per-minute trigger calls the tick endpoint (today a host-level scheduled task). There is no in-process timer. After a gap, one run fires and the other missed slots are counted, not back-filled. Timezone is stored, but schedules evaluate in server time.
Hardening items before productionAPI-wide rate limiting (only login and registration are limited today). A Content-Security-Policy header (the other security headers are set). Enforcement of access-token scopes, and per-user data isolation on the MCP-server read tools (the audit tool is already scoped). One DNS-pinned guard for all outbound fetches. An atomic nonce claim and idempotent retry for confirmed MCP writes. Secure defaults, a managed scheduler trigger, key management, observability, backups and CI/CD. §5 lists the full set.
AuthenticationEmail and password only; there is no SSO. The auth library is Auth.js v5 beta (next-auth 5.0.0-beta.31), a pre-release of its v5 major version.
Key managementAll per-user credential keys derive from one server master secret. There is no KMS/HSM integration or key rotation tooling yet.
ObservabilityLogging goes to the console only. There is no structured logger, APM or tracing. Cost figures use a manually maintained price table, flagged in code as possibly stale.
Container imagesTwo auxiliary images (metasearch, database admin UI) track latest rather than pinned versions. The admin UI is a development convenience; before production it should be bound to a private interface or dropped from the stack.
Remote monitoring detailSessions pushed by remote collectors carry metadata only, so the per-session tool waterfall works only for transcripts on the server host.

5.3 Phase 3 — scale-out

Replace the in-process event bus and limiters with a shared store, and move the scheduler trigger into the product. This removes the external trigger, adds timezone/DST handling and catch-up, and makes crash-resume safe with multiple workers (row claims already use FOR UPDATE SKIP LOCKED). Also forward remote-collector events so session detail works for every machine. Then run several stateless app instances behind a load balancer.
