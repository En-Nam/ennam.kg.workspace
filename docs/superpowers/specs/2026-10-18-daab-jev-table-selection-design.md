# DAAB: optional Jev judge for NL→SQL table selection — Design

Date: 2026-10-18 · Status: draft for review · Path: architectural

## 1. Problem and goal

Every NL→SQL plan in DAAB is generated by the `nl_query_intent` call. Smart context (embedding
search plus AI table filter, BA-020) is **not running** in any environment we checked. So the
planner gets the **whole schema** of the data source via `buildLegacyContext`, capped at
`schemaContextMaxChars = 60000`.

Measured on the dev DB, last 60 days:

- `nl_query_intent` averages **~11k input tokens**, p50 2.8s / p90 6.8s.
- `ai_queries` shows 3431 `completed` (p50 33ms, mostly plan-cache hits), 106 `clarification_needed`
  (p50 2.5s, and the user gets no answer) and 36 `failed`.

Most of a question's tables are irrelevant to it. Sending only the needed ones gives the planner
fewer tokens to read and fewer wrong tables to confuse it.

"Is this table needed for this question?" is a yes/no decision per table, which is exactly what
Jev (TypeSafe's typed judge model) does. Jev generates no text and returns a calibrated
probability per question in ~70–500ms server time, at $0.042 per million input tokens. One request
can carry one question per table.

**Goal:** when Jev is configured and switched on, DAAB asks it which tables a question needs and
sends only those to the planner. When Jev is missing, off, slow or failing, DAAB behaves exactly as
it does today.

**Success criteria**

1. With no `TYPESAFE_API_KEY`, or with the setting `off`, behaviour and latency are identical to
   today. Existing tests pass unchanged.
2. In `shadow` mode the request path does not get slower: Jev runs off the request path and its
   decision is logged next to what the plan actually used.
3. In `on` mode, any Jev failure falls back to the full schema (today's behaviour). Jev can never
   cause a user-visible error.
4. A repeated question costs no Jev call while its selection is cached (§4.4).
5. An offline replay over historical queries reports recall, schema-size reduction and real
   latency (including the network round trip) before anyone switches to `on`.

## 2. Out of scope

- **Turning on smart context** (embedding provider, `table_embeddings` backfill). That is a separate
  project with its own behaviour change. Jev here plugs into the path that actually runs.
- LAAM (a separate spec follows; only its env variable names are reserved here, §6).
- The GraphRAG answerability gate, a clarification judge, and replacing `sql_verification`.
  These are later candidates once this one has numbers.
- Per-project or per-data-source switches. v1 has one global setting, and the per-environment key
  is the data gate (§7).
- The Python worker and agentic path.
- Counting Jev spend against `ai.monthly_budget_usd`. It is logged, not budgeted.

## 4. Design

### 4.1 Configuration

Env (kg-server), all optional. Names follow TypeSafe's own SDK:

| Variable | Default | Meaning |
|---|---|---|
| `TYPESAFE_API_KEY` | empty | No key → Jev unavailable, every judge mode behaves as `off` |
| `TYPESAFE_BASE_URL` | `https://api.typesafe.ai` | API root |
| `TYPESAFE_DEFAULT_MODEL` | `jev-1.13.0` | **Pinned version**, not `jev-latest`: thresholds are tuned per version and the alias moves |
| `TYPESAFE_TIMEOUT_MS` | `800` | Hard budget for one Jev call in the request path |

System settings (web, admin only), seeded by migration:

| Key | Values | Default |
|---|---|---|
| `ai.judge.table_filter` | `"off"` \| `"shadow"` \| `"on"` | `"off"` |
| `ai.judge.table_filter_threshold` | number in (0,1) | `0.2` (smoke test: the lowest score of a needed table was 0.33, so 0.3 leaves almost no margin; see §5.0) |
| `ai.judge.table_filter_max_tables` | integer | `60` (sources with more tables skip Jev and keep the full schema) |

The threshold leans toward recall on purpose (0.2 rather than the 0.3 first proposed). Dropping a needed table produces a wrong or clarified
answer; keeping an extra one only costs tokens. It is tuned from shadow and replay data.

### 4.2 Jev client (package location: builder's call)

- Thin HTTP client for `POST {base}/v1/systemone`: Bearer auth, JSON body
  `{ "model", "state", "questions" }`. A `noul` answer is `{ "type": "noul", "noul": p }`. The
  response carries the versioned `model` and `usage.input_tokens`.
- `nil` client when the key is empty; callers check availability, not env.
- **No retries in the request path** (the official SDKs retry 429/529 by default; we must not).
  One attempt, bounded by `TYPESAFE_TIMEOUT_MS` through the request context.

### 4.3 The selection request

Called from the legacy path, after `GetSchemaTree` and before `buildSchemaContext`, when the source
has 2 to `max_tables` tables. One request, one `noul` question per table:

```json
{
  "model": "jev-1.13.0",
  "state": { "question": "<user NL question, PII-masked (§4.7)>" },
  "questions": {
    "t0": { "type": "noul",
            "instructions": {
              "table": { "name": "public.sales",
                         "description": "<tableDescription, ≤200 chars>",
                         "columns": ["sale_id", "store_id", "sold_at", "total_amount", "..."] },
              "question": "Is `table` needed to answer `state.question` with SQL — as a source of rows, a filter, or a join between other needed tables?" },
            "criteria": { "true": "The query must read or join this table",
                          "false": "The answer does not depend on this table" } },
    "t1": { "...": "..." }
  }
}
```

- Column **names only**, no types, descriptions or sample values. That keeps the request small and
  carries no row data.
- Selection = tables with `p ≥ threshold`. Then call `buildSchemaContext` on a tree pruned to the
  selection, keeping the original order.
- **Join bridges:** also keep any table that has a foreign key to or from two or more selected
  tables. A dropped bridge makes a join impossible, and this rule is cheap. Whether to widen it to
  all 1-hop FK neighbours is decided from replay numbers.
- Empty selection → use the full schema (`outcome=fallback_empty`).
- The question wording above is the starting point. The builder tunes it against the replay (§5).

### 4.4 Selection cache and the plan cache

The selection decides the schema text, and the schema text is part of the plan-cache key. So:

- **Selection cache**, in-process LRU with TTL (size/TTL: builder's call):
  - Key: `(data_source_id, normalizeNLQuery(question), schema-tree hash, judge model, threshold)`.
  - Value: the selected table names.
  - Only `ok` outcomes are cached. A timeout or error falls back to the full schema for that
    request only, and the next miss tries Jev again.
- A fallback request builds the full-schema text, i.e. today's fingerprint, so it still hits
  today's plan-cache entries.
- Jev is deterministic for the same input, so a cached or recomputed selection gives the same
  fingerprint, and the plan cache keeps hitting for repeated questions.
- **Known costs:**
  - On the first switch to `on`, existing plan-cache entries (keyed on the full schema) stop
    matching for questions Jev narrows, so the cache re-warms.
  - After a server restart, the first ask of each question pays one Jev call even when its plan is
    cached.
  - Both are accepted for v1. If they matter, persist the selection cache in the DB later.

### 4.5 Modes

| Mode | Request path | Off the request path |
|---|---|---|
| `off`, no key, or table count outside 2..max | today's behaviour | — |
| `shadow` | today's behaviour (full schema) | on a selection-cache miss, run the Jev selection in a detached goroutine (bounded concurrency, e.g. semaphore of 4, drop when full) and log it |
| `on` | Jev selection → pruned schema; on timeout, error or non-2xx → full schema | — |

### 4.6 Logging: new table `ai_judge_logs` (migration `000094`)

This is a separate table, not `ai_usage_logs`. Jev has no `ai_providers` row and must not get one,
so that routing can never pick it.

| Column | Notes |
|---|---|
| `id`, `created_at` | |
| `request_type` | `table_filter` |
| `mode` | `shadow` \| `on` |
| `outcome` | `ok` \| `timeout` \| `error` \| `fallback_empty` |
| `error_code` | HTTP status or transport class |
| `model` | versioned id returned by Jev |
| `latency_ms`, `input_tokens` | measured client-side, network included |
| `data_source_id`, `query_hash` | no raw question text |
| `table_count`, `selected_count` | |
| `scores` | jsonb `{table: p}` |
| `selected` | jsonb list (after bridge rule) |
| `plan_tables` | jsonb, filled after planning: tables referenced by the final plan (nullable) |
| `schema_chars_full`, `schema_chars_used` | size reduction |

In shadow mode the plan is built from the full schema, so `plan_tables ⊄ selected` means Jev would
have dropped a table the planner actually used. That is the live recall signal.

### 4.7 PII masking

Before the question goes into `state`, replace email addresses and phone-number-like digit runs
(Vietnamese formats included) with placeholders. Table selection does not need them. The masked
question is used only for the Jev request; the planner keeps the original.

### 4.8 API and UI

- `AIFunction` gains `SupportsJudge bool`. Add an entry for this judge (key builder's call, e.g.
  `nl_table_select`) so it is described in plain language on the settings page. It has no LLM model
  assignment.
- `GET /ai-functions` adds `judge_supported`, `judge_available` (key present) and `judge_mode`.
- Settings validation: `ai.judge.*` keys accept only the values in §4.1 (400 otherwise).
- In `ennam.kg.next` the AI settings page shows an Off / Shadow / On control for it. When
  `judge_available=false` the control is disabled with the hint "Jev key not configured on the
  server". Admin only.

### 4.9 Separate bugfix in the same branch: the two settings-key mismatches

Make `resolveDefaultTier` read `ai.query_tier` and `resolveTopK` read `ai.context_top_k`. This has
**no runtime effect today**, because `ContextBuilder` is not constructed (§3). It only makes smart
context honour its settings once someone enables it. Ship it as its own commit with its own test.

## 5. Verification

0. **Smoke test before any code** (needs the key). Run 20 calls from this machine and from the
   kg-server host, using Vietnamese pharmacy questions and the real 25-table pharmacy schema.
   - Record client-side p50/p90 latency.
   - Eyeball the selections.
   - If p90 exceeds `TYPESAFE_TIMEOUT_MS`, stop and revisit the budget.

   **Done 2026-10-18, from the developer machine in Vietnam.**

   Setup:
   - `jev-1.13.0`, pharmacy source, 25 tables / 294 columns.
   - 200 distinct historical questions (100 Vietnamese, 100 English), about 2/3 of them needing
     2 or more tables.
   - Gold = the tables referenced by the SQL each question produced.

   Results:
   - 200/200 calls OK.
   - Client latency p50 399ms / p90 438ms / max 665ms. Input ≈ 4.4k tokens per call, so
     ≈ $0.0002 per call.

   | Threshold | Recall | Questions with every needed table kept | Tables kept (avg) | Columns sent vs full |
   |---|---|---|---|---|
   | 0.2 | 1.000 | 200/200 | 7.0 / 25 | 29% (p90 55%) |
   | 0.3 | 1.000 | 200/200 | 5.7 / 25 | 24% (p90 47%) |
   | 0.5 | 0.989 | 196/200 | 4.1 / 25 | — |

   - Vietnamese and English scored the same.
   - The lowest score of a needed table was 0.33, hence the 0.2 default.
   - Caveats:
     - the gold is what past plans used, not hand-verified;
     - many questions are templated test phrasings from one source;
     - the kg-server host's network path is not measured yet.

   Shadow mode (step 4) is still required.
1. **Unit:**
   - threshold, bridge rule and empty-fallback;
   - the mode table in §4.5 against a fake Jev server: ok / timeout / 500 / 429, and 429 must not
     retry;
   - `nil` client ⇒ off;
   - the table-count bounds;
   - only `ok` is cached, and a cache hit makes no judge call;
   - PII masking;
   - settings validation.
2. **Regression:** existing query-intent and plan-cache tests pass with no key set.
3. **Offline replay CLI** (`cmd/jev-eval`, read-only DB access):
   - Input: the last N `ai_queries` with `generated_sql`.
   - Run the Jev selection on each and compare it against the tables referenced in
     `generated_sql`.
   - Report:
     - recall (needed tables kept),
     - mean kept / total,
     - schema-char reduction,
     - Jev latency p50/p90,
     - the Vietnamese-question subset separately.
   - Proposed bar for `on`, to be confirmed by the owner:
     - recall ≥ 0.98,
     - schema text −40% or better on the pharmacy source,
     - Jev p90 under the timeout.
4. **Shadow in the dev stack** for a few days. Then compare the `plan_tables ⊄ selected` rate and
   latency before switching to `on`. After switching, compare `nl_query_intent` input tokens and
   latency, and the clarification and failed rates, against the 60-day baseline in §1.

## 6. Environment variables to define now

**DAAB** (`.env` → `docker-compose.yml` kg-server `environment:`):

```

TYPESAFE_BASE_URL=https://api.typesafe.ai
TYPESAFE_DEFAULT_MODEL=jev-1.13.0
TYPESAFE_TIMEOUT_MS=800
```

**LAAM** (`LAAM/.env`): same names and meaning. Reserved for the LAAM spec and unused until then.

`.env.example` gets the four lines. `.env.release.example` gets them with `TYPESAFE_API_KEY` left
empty and the comment: *"Needs owner approval before filling — see §7."* For DAAB, the compose
passthrough lines are part of this work.

## 7. Data policy (owner-approved 2026-10-18)

What leaves the server: the user's question (PII-masked), table names, table descriptions and column
names. No row data.

- **Dev / demo environments:** allowed.
- **Customer environments:** only after all three of the following hold:
  - TypeSafe's DPA has been reviewed, and zero data retention is available on our plan
    (today it is enterprise-only);
  - the customer has agreed;
  - shadow results on dev meet the §5 bar.
- **Mechanism:** whether an environment gets `TYPESAFE_API_KEY`. No key, no Jev. There is no
  separate code gate.

## 8. Risks

- **Vietnamese quality.** TypeSafe states English is best and that other languages are "handled
  but not equally well". This is the main reason for replay and shadow before `on`.
- **Network latency** to TypeSafe is unknown until the smoke test.
- **Vendor maturity.** Jev launched 2026-09-15. Mitigated by pinning the version, keeping it off
  by default, and falling back to the full schema.
- **Large sources** (over `max_tables`) get no benefit in v1. That is accepted; smart context is
  the path for them.

## 9. Anti-goals

- A user-visible failure caused by Jev.
- Repeated questions getting slower.
- Jev appearing in LLM provider routing or the model-assignment dropdowns.

## 10. Decisions

Owner:

- Plug Jev into the legacy path (option B); smart context is a separate project.
- Data policy as in §7.

Mine, open to change:

- one global setting;
- threshold 0.2 (from the smoke test);
- timeout 800ms;
- max 60 tables;
- column names only in the request;
- the bridge rule;
- the in-process selection cache, caching only `ok` outcomes;
- the separate `ai_judge_logs` table;
- Jev not counted in the AI budget;
- the settings-key fixes shipped as a separate commit.
